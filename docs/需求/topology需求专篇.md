## 0. 完成情况总览

> 一句话：**共 34 条需求，全部 ⏳**（本专篇为立项，尚未开工）。
> 现有实现是**从数据库读边、用中文子串猜节点类型**，没有状态机、没有迟滞、没有真正的优化算法。

**现有资产映射**

| 现有实现 | 位置 | 已有 | 缺什么 |
|---|---|---|---|
| `linkTopology()` | `backend/src/api/Api.cc` L648–674 | 读 `link` 表 → 去重产出 `nodes` + 原样返回 `edges` | **节点类型靠中文子串猜**：`n.find("云端")` → `cloud`、`"边缘"` → `edge`、`"前沿"` → `forward`（L661–666）。**这是把规则写进引擎的典型**，且换一套命名即失效 |
| `linkMetrics()` | `Api.cc` L676–678 → `linkMetricsJson()` L85 | 返回 4 项评估（链路稳定度/覆盖率/协同效率/抗干扰能力，见 L85 起的实现） | 口径是否可复算需核；无迟滞 |
| `optimizeLink()` | `Api.cc` L680–690 | 广播 `telemetry.link.quality{meshProgress, state:"green"}` | **演示级硬编码**：`UPDATE link SET state='green', signal='strong', bandwidth*1.12, latency*0.72, mesh_progress=MIN(100,+20)`（L684–685）。是 SQL 改数，不是算法 |
| `linkCurves()` | `Api.cc` L692–709 | 产出带宽提升 / 时延降低两条曲线 | **公式写死**：`bw = 46 + 46*(1-exp(-3.2t))`、`lt = 110*exp(-2.8t)+22`（L700–701）；时间基准是 `nowMs - 15min`，与真实数据无关 |
| 前端 | `useStore.ts` `applyWs` link case L547–567 | 把**驼峰事件字段归一成下划线台账列名**（`bandwidthMbps`→`bandwidth_mbps` 等，含注释说明"此处做一次性归一"） | 这次归一**应在引擎侧完成**，前端不应承担 |
| 前端 | `useStore.ts` `refreshLinks`/`optimizeLink` | REST 调用 | 无逻辑 |
| 图元契约 | `map-2d` `LinkItem{id, from, to, state?: green\|yellow\|red}`、`ClusterItem{id,lng,lat,name}` | **渲染侧齐备** | 无需改动 |

**关键差距（本专篇主要价值）**

> 1. **拓扑的节点类型是"猜"出来的**（中文子串匹配）。`模块划分与缺口分析.md` §3.5 已指出：
>    引擎该补的是"节点与边从哪来、摆在哪、状态怎么算"，**不是靠名字猜**。
> 2. **"优化"是 SQL 改数**，不是算法；且 `bandwidth*1.12` 这类乘数一旦跑两次就会累积。
> 3. **曲线是写死的公式**，与真实链路数据无关——现场问"带宽提升曲线怎么来的"答不出来。
> 4. **没有迟滞**：链路在阈值附近会反复绿黄红抖动（界面观感问题，也是需求初稿 §3.7 "链路状态色"的可靠性前提）。

## 1. 定位与边界

### 1.1 定位

```
输入：链路观测（来自 device-ingest 归一化事件 / 模拟源）
   │
   ▼
┌──────────────────────────────────────────────────────────┐
│  topology（C++，无 Web 框架、无 SQL）                      │
│  MODEL 拓扑模型 → Q 质量聚合 → ST 状态机（含迟滞） →         │
│  EVAL 网络评估 → OPT 优化建议                              │
│                      │                                   │
│                      └──► 出口：ITopologySink（宿主实现）    │
└──────────────────────┬───────────────────────────────────┘
                       │ 拓扑 + 边上状态码（不含颜色语义）
                       ▼
   宿主：落库 + 广播 telemetry.link.quality ｜ view-composer：转成图元 ｜ map-2d：画
```

**一句话**：topology 回答"**拓扑长什么样、每段链路什么状态、整体评估如何、怎么优化**"。
它**不产出颜色**（`green/yellow/red` 由 `map-2d` 的图元语义决定，见 D4），也不产出曲线图（曲线是输出，画是别人的事）。

### 1.2 为什么必须是独立引擎

1. **`map-2d` 只提供了图元，没提供拓扑语义**：`LinkItem` 要 `from`/`to` 坐标，`ClusterItem` 要坐标——**这些从哪来、状态怎么算，正是本引擎的活**（`模块划分与缺口分析.md` §3.5 关键设计点 1）。
2. **迟滞是可靠性要求**：没有它，界面颜色会抖。
3. **它有两个消费者**：换一套系统，节点类型与阈值会变，但**拓扑模型 + 质量聚合 + 状态机相同**。
4. **它有真实输入源**：`device-ingest` 已能产出设备级健康与丢包乱序统计，链路质量可以由它派生。

### 1.3 范围边界

| 做 | 不做 |
|---|---|
| 拓扑模型：节点、边、层级（网状 / 三层），**由规则声明结构** | 🚫 不含节点类型名（`云边端`/`前沿指挥节点` 属规则） |
| 节点布局的**坐标来源**（场景给定 / 从集群位置派生） | 🚫 不做地图渲染与符号（`map-2d`） |
| 质量聚合：信号、带宽、时延、丢包、覆盖、组网进度、节点负载、缓存 | 🚫 不做设备收包与健康统计（`device-ingest`，本引擎**消费**其事件） |
| 状态机：分段状态判定 + **迟滞**（防抖） | 🚫 不做颜色与样式（`map-2d` 图元 `state` 字段） |
| 网络评估：稳定度、覆盖率、协同效率、抗干扰能力 | 🚫 不做方案评分（`scoring` 读本引擎结论） |
| 优化：在可声明搜索空间内给出改进后的建议值 | 🚫 不做 SQL 改数（现状做法，见 D2） |
| 链条曲线输出（带宽/时延随时间） | 🚫 不做曲线绘制（前端图表） |

### 1.4 硬约束

| 约束 | 取值 | 依据 |
|---|---|---|
| 现有接口形状 | `/links/topology` 返回 `{nodes, edges}`；`/links/metrics`、`/links/curves` 形状**不得破坏** | 契约 §3.4；`Api.cc` L648–709 |
| `telemetry.link.quality` 事件 | 负载含 `{linkId, from, to, signal, bandwidthMbps, latencyMs, lossRate, coverageKm2, meshProgress, state:"green"\|"yellow"\|"red"}` | 契约 §4 |
| 归一责任 | 事件用**驼峰**、台账用**下划线**；现状由前端做一次性归一（`useStore.ts` L548 注释）→ **MUST 上移到引擎** | D3 |
| 图元对接 | 输出 MUST 可映射到 `map-2d` 的 `LinkItem{id, from, to, state}` 与 `ClusterItem{id,lng,lat,name}` | `map-2d` 接口文档 §3.3 |
| 刷新频率 | 链路质量指标 1 秒刷新 | `TR-MSG-06` |
| 状态取值 | `green`/`yellow`/`red` 三值（与 `map-2d` 图元枚举一致） | `map-2d` 接口文档 §3.3 |
| 语言/构建 | C++17 + CMake ≥ 3.20；仅 `nlohmann/json` | 对齐既有 C++ 模块 |

## 3. 功能需求条目

### 3.1 拓扑模型（TPL-MODEL）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| TPL-MODEL-01 | **MUST** 节点类型由规则声明（`{ key, 名称, 层级, 图形建议? }`），引擎 MUST NOT 内建类型名，且 **MUST NOT 用名称子串推断类型** | 全仓检索 `云端`/`边缘`/`前沿` 作为**判断依据**零命中；把节点改名后类型不变 | ⏳ |
| TPL-MODEL-02 | **MUST** 支持两种结构：平铺网状 与 多层（层数、层间关系由规则声明） | 同一份数据分别按两种结构装载均可渲染 | ⏳ |
| TPL-MODEL-03 | **MUST** 节点坐标来源可注入（场景给定坐标 / 由集群位置派生 / 由外部布局算法给出），引擎 MUST NOT 硬编码坐标 | 换坐标源即换布局 | ⏳ |
| TPL-MODEL-04 | **MUST** 边的声明与去重：无向边 MUST 去重（现状用 `seen` 集合，保留该语义），自环 MUST 被拒绝 | 重复边只出现一次；自环报错 | ⏳ |
| TPL-MODEL-05 | **MUST** 拓扑校验：孤立节点、悬挂边（端点不在节点集）、层级越级连接 MUST 可检出并给可读原因 | 人为制造悬挂边 → 检出并定位 | ⏳ |
| TPL-MODEL-06 | **SHOULD** 拓扑快照导出入（供审计与回放复盘） | 导出/导入后拓扑一致 | ⏳ |

### 3.2 质量聚合（TPL-Q）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| TPL-Q-01 | **MUST** 指标集可配：key、单位、方向（越大越好/越小越好）、有效范围；引擎 MUST NOT 内建指标名 | 换指标集即换聚合维度 | ⏳ |
| TPL-Q-02 | **MUST** 事件归一在引擎内完成：驼峰事件字段 → 台账字段的映射 MUST 由引擎负责（**MUST NOT 留给前端**） | 全仓检索 `bandwidthMbps` 在前端侧零命中；引擎提供单一形状 | ⏳ |
| TPL-Q-03 | **MUST** 缺失字段按"保持原值"处理，MUST NOT 用 0 或默认值覆盖（现状前端即按 `?? e.xxx` 保持原值，保留该语义） | 只带 `state` 的事件不破坏其它指标 | ⏳ |
| TPL-Q-04 | **MUST** 滑动窗口聚合：以可配窗口（默认 1 s，对齐 `TR-MSG-06`）计算均值/极值，供状态机与评估使用 | 灌入已知序列，聚合结果可手算核对 | ⏳ |
| TPL-Q-05 | **MUST** 按边与按节点双维度聚合（节点质量由其关联边派生，口径可配） | 节点指标可复算 | ⏳ |
| TPL-Q-06 | **SHOULD** 覆盖率与组网进度口径显式：`覆盖率`、`meshProgress` 的计算方式可配且可复算 | 同输入手算一致 | ⏳ |

### 3.3 状态机与迟滞（TPL-ST）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| TPL-ST-01 | **MUST** 阈值可配：`green`/`yellow`/`red` 的分档阈值由规则声明，引擎 MUST NOT 硬编码 | 调阈值后状态变化可复现 | ⏳ |
| TPL-ST-02 | **MUST** 迟滞（防抖）：状态向上/向下迁移 MUST 使用**不同阈值**或**连续 N 次确认**，避免阈值附近抖动 | 构造在阈值附近震荡的输入序列 → 状态变更次数显著低于越阈次数 | ⏳ |
| TPL-ST-03 | **MUST** 最小驻留时间：状态变更后 MUST 在该状态驻留至少可配时长 | 高频越阈输入下状态变更不超过理论上限 | ⏳ |
| TPL-ST-04 | **MUST** 状态变更可解释：每次变更 MUST 记录"从哪到哪、哪个指标越阈、当时数值" | 变更日志可复原判定过程 | ⏳ |
| TPL-ST-05 | **MUST** 状态输出保持三值枚举 `green`/`yellow`/`red`（对齐 `map-2d` 图元） | 输出与图元枚举可直接对接 | ⏳ |
| TPL-ST-06 | **SHOULD** 手动覆盖：允许人工把某条边标为某状态，并可解除（对齐初稿"AI 自动优化链路"的交互） | 覆盖期间自动判定不生效；解除后恢复自动 | ⏳ |

### 3.4 网络评估（TPL-EVAL）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| TPL-EVAL-01 | **MUST** 四项评估（稳定度/覆盖率/协同效率/抗干扰能力）算法可配、输入显式、结果可复算 | 任取一份输入，四项均可手算核对 | ⏳ |
| TPL-EVAL-02 | **MUST** 评估为结构化输出（数值 + 逐项依据），**不含自然语言结论**（如"支持三集群并行数据回传"这类话术归 `llm-provider`） | 输出中无成句文案 | ⏳ |
| TPL-EVAL-03 | **MUST** 评估结论供 `scoring` 读取（作为评分输入项"链路稳定度"） | `scoring` 只读调用即可拿到数值 | ⏳ |
| TPL-EVAL-04 | **SHOULD** 阈值提示：低于可配下限时给出"不满足实时控制要求"这类**结构化**判定（布尔 + 依据） | 判定可复现 | ⏳ |

### 3.5 优化（TPL-OPT）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| TPL-OPT-01 | **MUST** 替换现状 SQL 改数：`state='green'` + `bandwidth*1.12` + `latency*0.72` + `mesh+20` 这类硬编码 MUST 移除 | 全仓检索 `1.12`/`0.72`/`+20`/`'green'` 作为优化实现零命中 | ⏳ |
| TPL-OPT-02 | **MUST** 优化基于可声明搜索空间（哪些参数可调、步长、上下限），产出**建议值**而非直接改状态 | 换搜索空间即换优化行为；优化只产出建议 | ⏳ |
| TPL-OPT-03 | **MUST** 幂等：连续优化同一拓扑 MUST 不产生累积效应（现状乘数会累积，属缺陷） | 连续调用 10 次，结果收敛不漂移 | ⏳ |
| TPL-OPT-04 | **MUST** 优化结果可解释：输出"改了哪些参数 → 哪些指标变化 → 评估变化" | 前后对比可逐项核对 | ⏳ |
| TPL-OPT-05 | **MUST** 单调性：优化后整体评估 MUST NOT 变差，否则返回"无改进" | 构造无改进场景 → 返回"无改进" | ⏳ |
| TPL-OPT-06 | **SHOULD** 曲线输出基于真实数据：带宽/时延曲线 MUST 由滑动窗口的真实聚合值产生，**MUST NOT 用写死公式** | 全仓检索 `exp(-3.2`/`exp(-2.8` 零命中；曲线点来自真实窗口 | ⏳ |

### 3.6 非功能性（TPL-NFR）

| 编号 | 需求描述 | 验收标准 | 状态 |
|---|---|---|---|
| TPL-NFR-01 | **MUST** 零外部依赖：无 Web 框架、无 SQL（持久化走注入的 `ITopologyStore`）；不依赖其它引擎内部 | 空环境独立构建；跨仓 import 零命中 | ⏳ |
| TPL-NFR-02 | **MUST** 出口为反向接口：`ITopologySink` 由宿主实现用于落库与广播 | 引擎内无落库与广播 | ⏳ |
| TPL-NFR-03 | **MUST** 时间可注入（`IClock`），使迟滞与窗口测试可复现 | 注入假时钟测试通过 | ⏳ |
| TPL-NFR-04 | **MUST** 确定性：同输入同输出（含迟滞状态机） | 同序列跑两次结果一致 | ⏳ |
| TPL-NFR-05 | **MUST** 独立交付：独立构建、独立示例、独立测试、独立验收脚本（退出码 0/1） | 空环境 clone → 一条命令构建 → 一条命令验收 | ⏳ |
| TPL-NFR-06 | **SHOULD** 性能：1000 条边、1 Hz 输入下，单次聚合 + 判定 P95 ≤ 1 ms | 实测达标 | ⏳ |

## 4. 引擎与规则的划分（policies）

| 属引擎（可复用） | 属规则（`policies/mapapp`，项目专属） |
|---|---|
| 拓扑模型、去重、校验、快照 | **节点类型与层级**：云端算力中心 / 边缘节点 / 前沿指挥节点 / 集群 |
| 质量聚合、事件归一、滑动窗口 | **指标清单**：信号强度、带宽、时延、丢包率、覆盖范围、组网进度、节点负载、缓存 |
| 状态机与**迟滞**、驻留时间、变更日志 | **绿黄红阈值、迟滞参数、驻留时长** |
| 评估框架与可复算输出 | **四项评估的算法与权重** |
| 优化框架（搜索空间、单调性、幂等） | **可调参数与步长、优化目标** |
| 曲线数据结构 | **曲线时间粒度与窗口长度** |
| 出口接口、时钟注入 | **节点坐标**、场景拓扑结构选择（网状 / 三层） |

**判据**：引擎公开接口里出现 `云端`/`边缘`/`前沿`**作为判断依据**、或 `1.12`/`0.72` 这类优化常量即破线。

## 5. 决策记录

| 编号 | 议题 | 决策 | 影响 |
|---|---|---|---|
| D1 | 引擎部署侧 | **后端 C++** | 全部条目 |
| D2 | "优化"的语义 | **产出建议值，由宿主决定是否落库**；引擎 MUST NOT 直接改状态。避免现状"跑两次乘两次"的累积缺陷 | TPL-OPT-01/03 |
| D3 | 事件字段归一在哪做 | **引擎内**（上移）。前端 `applyWs` 的 link case 归一逻辑应被删除，前端只消费统一形状 | TPL-Q-02 |
| D4 | 颜色语义归属 | 引擎只出 `green/yellow/red` **状态码**；颜色到像素的映射属 `map-2d` 主题 | TPL-ST-05；`模块划分与缺口分析.md` §3.5 关键设计点 2 |

## 6. 风险

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | 移除写死曲线后，界面曲线可能变"平淡" | 演示观感下降 | 用模拟源灌入有意义的数据序列；曲线形状由数据决定 |
| R2 | 迟滞参数配置不当导致"该变不变" | 界面失真 | 迟滞参数可配 + 变更日志可查；给一组推荐默认值 |
| R3 | 拓扑模型抽象过度（做成通用图引擎） | 配置地狱 | 只支持"节点 + 边 + 可选层级"，**不做路由计算、不做图算法库** |
| R4 | 优化搜索空间过大导致超时 | 接口卡顿 | TPL-OPT-* 设迭代上限与时限，超时返回已得最优并说明截断 |
| R5 | `map-2d` 的 `LinkItem` 需 `from`/`to` **坐标**，而拓扑边是节点对 | 对接时缺坐标 | TPL-MODEL-03 保证节点坐标可用；宿主做节点→坐标映射 |
| R6 | 与 `scoring` 的"链路稳定度"重复实现 | 两份口径 | 稳定度**只由本引擎算**，`scoring` 通过接口读取 |
